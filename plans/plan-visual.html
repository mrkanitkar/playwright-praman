1. Executive Summary

Praman v1.0 (playwright-praman on npm) is a ground-up rebuild of SAP UI5 test automation for Playwright. Not a port of dhikraft v2.5.0 — new code, new architecture, informed by lessons learned.

Design Goals

  • AI-First — Native support for AI agents (Copilot, LLM-based test generators) as first-class consumers
  • Enterprise-Grade — Strict TypeScript, pino logging, security hardening, SAP certification readiness
  • Future-Proof — Browser scripts decouple UI5 versions; PlaywrightCompat decouples Playwright versions. Bridge adapter abstraction was removed in Phase 3 as premature.
  • Plug-and-Play — Single npm install playwright-praman with zero-config defaults

Key Architectural Change (Phase 3)

Bridge Adapter Layer REMOVED

The BridgeAdapter abstraction (ClassicUI5/WebComponent/Hybrid) was removed in Phase 3. It was premature abstraction that caused a critical data-loss bug. Proxy now calls page.evaluate() directly. Browser scripts are the correct abstraction boundary.

5.4 Lessons Learnt — Architecture Simplification

Critical Bug: Premature Abstraction Caused Data Loss

The BridgeAdapter's executeControlMethod() returned result.value instead of the full MethodExecutionResult, stripping returnType, uuids, and objectTypes needed for sub-proxy creation. This broke the entire aggregation/object return chain.

Key Lessons

  1. Premature abstraction caused data loss — Adapter introduced for future WebComponent/Hybrid, but it broke result forwarding
  2. dhikraft's pattern is proven — Single proxy with direct page.evaluate() works because the proxy NEEDS full result context
  3. Adapter boundary was wrong — The real abstraction is browser scripts (UI5 API) vs node proxy (Playwright API)
  4. Inline return handling is correct — Separating required passing full state through params; inlining gives natural access
  5. Fewer files, better cohesion — 5 proxy files → 2 improved cohesion for tightly coupled code
  6. page.evaluate() serialization is #1 footgun — Module-level functions NOT available in browser; unit tests give FALSE POSITIVES
  7. Fixture assembly pattern works — mergeTests() cleanly composes independent fixture files
